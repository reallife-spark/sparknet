## Step 24 — signed delegated-compute capability (design proposal)

Prompted by the operator's "use the master and peer nodes to calculate 2-2"

so it was not done.

Operator then asked to spec a real one. Wrote **`COMPUTE_CAPABILITY_DESIGN.md`**
at the fabric root (design-proposal status, precedent = `MCP_A2A_DESIGN.md`).

Core finding driving the design: **local compute is already free** — a peer is
authoritative for its own inference (`peer-node/AGENTS.md`) — so a `compute`
capability gating it would be a tax that cannot be withheld. The proposal specs
**`compute-serve`** instead: accept a Master-signed *delegated* task, execute it
within a closed whitelist, return an attested result. It is the second
`sensitive: true` capability, in the same risk direction as `guard-apply` (the
holder is the node made to run something).

Spec contents:
- Two-place vocabulary change: `contracts/capabilities.json` **and** the
  hard-coded `KNOWN_CAPABILITIES` frozenset in `shared/sparknet-authz.py`;
  `tests/test_contracts.py:103` asserts they are equal (and `definitions` ==
  `known_capabilities`), so a one-sided edit fails closed.
- New typed signer op `sign-compute-task`, modelled exactly on
  `_sign_guard_approval` (sorted-field canonical bytes, refuse unknown/blank/
  expired, ledger block); no "sign bytes" op ever.
- Task envelope (params inside the signature, `content_in_signature: true`,
  nonce/TTL), result attested by the executor's **node identity** key (permission
  vs provenance split).
- Ordered fail-closed executor checks mirroring the guard, plus unprivileged
  execution and `--execute-enabled` default-off.
- Closed operation whitelist `arith` (restricted AST) + `digest`; arbitrary
  code/`eval`/shell explicitly rejected.
- Port decision: recommend a new overlay-only `compute-exec`; guard-9090 reuse
  and push-receive piggyback rejected.
- Worked node131→node133 2−2 round trip, options table, adoption plan

## Cluster inference design — `sparknet-cluster` (fabric PLAN Step 25)

Operator asked for the cluster feature set: Master admin over all nodes; every
node runs Ollama (Docker) wired to its local KB and hosts an Open WebUI; send a
prompt to a chosen node and have it fulfilled there; any node can send work to
others; and a "send the prompt to the sparknet-cluster" setting so all connected
nodes contribute to one answer. Researched the tree (subagents were down —
`Cannot connect to API` — so read directly), then resolved the design with the
operator in Plan Mode. Decisions, all locked: control = **admin authority +
dispatched signed tasks** (never remote mutation); **per-node** Ollama + Open
WebUI (Master included); cluster-job authority **mode-dependent — Master
ratifies at n≥3, direct signed initiator at n=2**; **inference auto-executes on
a valid signature, actions stay guard/PPE-gated**; local prompts use the local
vault, **cluster jobs use the Master's shared vector DB served top-K** (no
replication); **Master holds the canonical cluster conversation**, each node
keeps its own session copy plus the initiator/Master records.

Wrote **`CLUSTER_INFERENCE_DESIGN.md`** at the fabric root (design-proposal
status). It specifies: the `sparknet.cluster-job.v1` / `cluster-result.v1`
envelopes (plan inside the signature; result attested by the executor's node
identity key; budget + absolute expiry); four division modes — `decompose`
(sub-question DAG), `shard` (disjoint chunks of the Master's top-K set),
`best_of_n`, `mixture` (bounded rounds) — with the initiator auto-selecting and
the Open WebUI toggle able to force one; the reduce step producing a merged
answer, deduped citations, contradiction callouts and a contribution map, with
one bounded extra round if coverage is short; the fan-out as **N separate 1:1
signed requests**, never a multicast bus; the mode-dependent authority; the
local-vs-shared knowledge split; the Open WebUI `local` / `node/<id>` / `cluster`
interface; session recording on initiator + Master + participants; Docker
packaging; and the security boundary (a poisoned shared index yields bad text,
not bad state). Rejected with reasons: multicast bus, Master-run remote
execution, tensor-parallel model sharding in v1, vector-DB replication,
auto-execute without an action guard.

**Adopted increment — the two capability names only.** Reserved
`cluster-dispatch` (initiate a job; not sensitive) and `cluster-serve` (accept a
subtask; **sensitive: true** — the second sensitive capability after
`guard-apply`, and in the *confidentiality* direction) in **both** places:
`contracts/capabilities.json` (`known_capabilities` + `definitions`) and the
hard-coded `KNOWN_CAPABILITIES` in `shared/sparknet-authz.py`
(`tests/test_contracts.py:103` holds the two sets equal). The closed vocabulary
is now `telemetry, p2p-sync, push-receive, guard-apply, cluster-vote,
cluster-dispatch, cluster-serve`. Reserving a name grants nothing — neither is
required by any code until adopted. Everything else in the note is proposed;
each follow-on lands in its own commit (signer op `sign-cluster-job`, node stack,
