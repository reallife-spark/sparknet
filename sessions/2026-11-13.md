## Runtime selection

- **`agx64` (64 GB, teacher/main):** `llama.cpp` / `llama-server` (CUDA,
  `sm_72`). Ollama fallback; MLC-LLM optional; TensorRT-LLM, ExLlamaV2 and vLLM
  not the path.
- **`agx32` (32 GB, student):** `llama.cpp` / `llama-server` for the text
  engine/student; **Ollama** for the peer's own AI stack (Open WebUI 11434) and
  fallback; MLC-LLM optional; TensorRT-LLM, ExLlamaV2 and vLLM not the path.

Why: `llama.cpp` is the most reliable GPU path and widest model support; the
`llama-server` gives the OpenAI API and the precontext controls. Ollama wraps
the same llama.cpp backend with an easy API but a harder GPU build. MLC-LLM is
a TVM compile; TensorRT-LLM/ExLlamaV2 are heavy/custom; vLLM is the dependency
problem being removed. The `vllm` service name, port 8000, `vllm-stub` CPU
profile and the embed/rerank/audio aux services stay stable; the new image is
`sparknet-llm:agx`.

## Model selection

Same Qwen version for teacher and student, so the tokenizer/family is shared
and the distillation is a clean transfer:

- **Teacher/main `agx64`:** Qwen3.6-35B **Q4_K_M** (the largest same-version
  model that fits 64 GB at the best responsive quantization; Q5_K_M/Q6_K only
  if the measured tokens/s is acceptable).
- **Student `agx32`:** Qwen3.6-27B **Q4_K_M** (the smallest Qwen3.6 release;
  there is no 0.6B/1.7B). The 16.8 GB GGUF fits the 32 GB peer.
- Fallback pair only if the teacher is switched to Qwen3: Qwen3-32B Q4_K_M +
  Qwen3-0.6B Q8_0.
- Retire the current `qwen3.5-9b` / `qwen3.8-27b` pair: different versions, not
  a clean distillation pair.
- The exact pair is confirmed after the Phase 0 model inventory (GGUF,
  tokenizer, license, memory, tokens/s). The `model-catalog`, `agent-models`,
  `ai-stack` and `distillation-schema` are updated in Step 108.

Xavier tuning: target `sm_72` (`CUDA_ARCHITECTURES=72`); Q4_K_M teacher,
Q8_0/Q4_K_M student; `--n-gpu-layers 99`; measured `--ctx-size`/`--parallel`;
MAXN (`sudo nvpmodel -m 0`, `sudo jetson_clocks`); watch `tegrastats`; the
136.5 GB/s unified-memory bandwidth is the bottleneck.

## External GPU trainer path (2026-11-14)

The operator chose an external GPU trainer for Step 111. agx32 remains the
collection, serving and export-control node: `sparknet-distill-daily.sh` now
collects traces, builds the dataset, and writes a keyless
`/mnt/ai/distill/bundles/sparknet-distill-<id>-<utc>.tar.gz`. The bundle
contains the dataset, `Dockerfile.distill-external` (Python >=3.10,
transformers 4.51.3, QLoRA, llama.cpp b9016), `train_lora.py`, the GGUF
exporter and a manifest; it carries no key, signer socket or vault.

The external host builds `sparknet-distill-external` and writes
`out/student-q4_k_m.gguf` plus `out/export.json`. `sparknet-distill-import.py`
verifies the SHA-256, signs with the peer key and uploads through the Master's
8091 student-artifact intake; the 4B copy is then refreshed on agx64 with the
idle-aware sync. The run is blocked only on access to an approved external GPU
host, not on the software path. `make ci` and the bundle/import tests are green.
