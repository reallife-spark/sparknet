## Decisions / gotchas (Phase 3/4)

- The console holds **no key**: `compose → (ask signer) → dispatch` keeps "can
  authorise" and "can execute" in different processes. A URL-only target cannot
  be signed-for (node id + fingerprint are inside the signature), so it is
  refused rather than half-bound.
- The bridge's `ADMIN_ENTITY_FIELDS` is the peer's enforcement; the console's
  `REQUIRED_ENTITY` is only a usage check — a **test** asserts they are equal
  against the peer's own source, so the two cannot drift (same anti-drift pattern
  as the shared canonical projections).
- `_read_admin_events` treats an **absent spool as an empty feed**, not an error
  (a node with no signups has nothing to report), and caps the response because
  the spool is append-only and unbounded.
- Master spec test `test_every_executable_directory_is_wired_to_something`
  requires the console filename in the Makefile — hence the `console` target.

### Phase E mutating legs — run live, and the console bug they exposed

Operator decision: run a **real signup**, then the signed `approve`/`role` legs.

- Signed up a throwaway account directly on the peer's Open WebUI

- **Bug found (third live defect):** `console approve node133 <id>` failed
  `ok:false status:400 reason webui-refused webui_status 400` with
  `{"detail": "We could not find what you're looking for :/"}`. A *direct* call to
  `POST /api/v1/users/<id>/update {"role":"user"}` on the peer returned 200, so the
  endpoint and token were fine. Root cause is in
  `master-node/services/sparknet-admin-console.py` `main()`: it built the entity as
  `build_entity(action, ([args.target] if args.target else []) + args.entity)`,
  i.e. it **prepended the target node** as the first entity field. For
  `approve node133 <id>` that made `user_id = "node133"`, so the bridge asked the
  WebUI to update a user named `node133` → `USER_NOT_FOUND` (400). Every user_id
  action (`approve`, `role`, `get_user`, `get_user_chats`) was affected; only
  `list_users`/`list_events` (no entity fields) had ever worked. The low-level
  `compose_request` was correct and tested — no test exercised the CLI entity
  mapping, which is why it slipped.
- **Fix:** `entity = build_entity(action, args.entity)` (the target names the node
  and is passed only as `spec=`). Added
  `test_main_maps_positional_entity_without_the_target` to
  `master-node/tests/test_admin_console.py` (asserts `approve …` → `{user_id}` and
  `role …` → `{user_id, role}`, target excluded). Committed.
- Deployed the fixed console to the live cluster2 bundle (not a git repo) and
  re-ran the legs:
  - `approve node133 3430de4d-…` → **200**, `role: pending → user`.
  - `role node133 <id> admin` → **200** (`role: admin`); then
    `role node133 <id> user` → 200 (restored).
