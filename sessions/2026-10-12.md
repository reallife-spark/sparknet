## Decisions / gotchas (Phase 3/4)

- The console holds **no key**: `compose → (ask signer) → dispatch` keeps "can
  authorise" and "can execute" in different processes. A URL-only target cannot
  be signed-for (node id + fingerprint are inside the signature), so it is
  refused rather than half-bound.
- The bridge's `ADMIN_ENTITY_FIELDS` is the peer's enforcement; the console's
  `REQUIRED_ENTITY` is only a usage check — a **test** asserts they are equal
  against the peer's own source, so the two cannot drift (same anti-drift pattern
  as the shared canonical projections).
- `_read_admin_events` treats an **absent spool as an empty feed**, not an error
  (a node with no signups has nothing to report), and caps the response because
  the spool is append-only and unbounded.
- Master spec test `test_every_executable_directory_is_wired_to_something`
  requires the console filename in the Makefile — hence the `console` target.

## Step 32 done — RFC 6962 Merkle transparency primitive (Arc C)

`shared/sparknet-merkle.py` is written, vector-pinned, gated. Verbatim RFC 6962
generators and RFC 9162 verifiers.

### What the module is
- `leaf_hash(entry)` = SHA-256(0x00 ‖ content), `node_hash(l, r)` =
  SHA-256(0x01 ‖ l ‖ r), `merkle_root(entries)` with the split at the largest
  power of two below the length (`1 << ((n-1).bit_length() - 1)`), and
  `MTH({}) == e3b0c442…` (SHA-256 of the empty string) — no exception.
- `inclusion_proof(index, entries)` + `verify_inclusion(entry, index, size,
  proof, root)`; `consistency_proof(first_size, entries)` +
  `verify_consistency(first, second, root1, root2, proof)`. Verifiers run the
  RFC 9162 §2.1.3.2 / §2.1.4.2 algorithms statement-by-statement and return
  `False` (never raise) on crafted, wrong-length, empty-but-required, or
  malformed proofs. Generators raise `MerkleError` on anything they cannot
  honestly satisfy (OOB index, empty tree, first_size OOB).
- String leaves decode as hex (any even length): the published short-leaf
  spelling and the 64-hex block-hash spelling both work; odd length,
  whitespace, non-hex, and non-bytes/str entries are refused rather than
  guessed (UTF-8 text vs hex bytes are two different trees).
- `sign_tree_head` / `verify_tree_head` / `tree_head_signable` delegate to
  `sparknet-authz.py` via the same by-path `_load_authz()` loader that
  provenance uses — the fabric keeps exactly one crypto implementation. The
  head is `TREE_HEAD_DOMAIN ‖ json({"size","root"})` with the node's key
  recorded as `node_pubkey_b64`, mirroring a ledger header.

    `public_key_b64`; `sig` verifies over the recorded hashes), then trust. The
    Master-signed registry resolves the co-signer's `owner_node` (a non-revoked
    entry whose `signature_b64` verifies under the registry's master key via the
    shared `authorization_message`); otherwise a `trusted_users` user.md
    snapshot must match `(owner_id, owner_node, key_fingerprint)`. A byte-intact

- `contracts/provenance-protocol.md`: a "Co-signatures" section narrating the
  trust rule — the online Master-registry resolver and the offline `user.md`
  snapshot fallback, and why an unknown signer is `untrusted` rather than
  `invalid`.
- Both `00_System/schema.yaml` files: `zones.tracking` now notes that
  `signature.co_signatures[]` is a sibling of the primary `sig`.

### Why it cannot break the primary signature

`note_hashes` computes the tracking hash from `unsigned_tracking(tracking)` —
`tracking` with the whole `signature` key removed. `co_signatures` lives *under*
`signature`, so appending one leaves the primary tracking hash, the primary
`sig`, and `owner_id` untouched. The note still verifies `valid`. This is also
the first signed field ever to be a **list of dicts**, so it exercises the Step
35 emitter fix (`_emit_map` list-of-dicts alignment) in a real note.

### The trust rule, precisely

A signature proves a key; it does not say whose. Two resolvers:

1. **Master-signed registry** (online): the co-signer's `owner_node` names a
   non-revoked authorization whose `signature_b64` verifies under the registry's
   own master key. The Master attested the node.
2. **Origin `user.md` snapshot** (offline fallback): the entry's `owner_id`,
   `owner_node` and `key_fingerprint` match a trusted user record.

Byte-intact but unresolved → `untrusted` (a stranger), distinct from `invalid`
(a forgery).

- `proposal_state` derives `submitted` / `reviewed` / `decided` (or `absent`)
  from the chain.
- `verify_proposal_chain(records)` re-checks each record's conversation root,
  `user_key_fingerprint` vs `user_public_key_b64`, and both signatures over
  `proposal_signable`, then the logical order (exactly one first proposal; ≤1
  decision; every review after the proposal and before the decision; ids agree)
  against a **bare list** — so a received bundle is verified the same way.
- CLI: `propose`, `submit`, `review`, `decide`, `verify`, `list`.

### Integrity is not identity

A record carries both public keys inline, so a receiver verifies with no local
key material — the same reasoning the co-signature entry gives. `verify_proposal_chain`
therefore proves *bytes + attestation + order*, not *who the signer is*. Identity
is resolved separately against the registry or a `user.md` snapshot. And a
verified chain is not an authority: an approved proposal still needs a signed
session grant to change anything.

### Two decisions the operator made

### The bundle rule (why records stay local)

`verify_approval_blocks` checks each event block's `data.signatures.user` against
the **local** user key. So mirroring a foreign author's block into a node's own
ledger would make that node's own `provenance-verify --strict` fail. The fix: a
bundle is the ordered union of records, but each node appends only the records it
authors — proposal on the proposer's ledger, review on its reviewer's, decision
on its owner's. `verify_proposal_chain` checks the union, so the receiver verifies
a chain whose records live on other nodes; a refused bundle appends nothing.
`test_each_node_records_only_its_own_records` proves A holds `[proposal, decision]`,
B holds `[review]`, and each ledger still passes `verify_approval_blocks`.
