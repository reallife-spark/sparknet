## The two defects

**The unbounded pin.** `pyproject.toml` pinned `chromadb>=0.5`, with no upper
bound, and Chroma's *default* embedding function is the one the library
fetches. A library upgrade could therefore swap the model under a live index,
and every distance returned afterwards would be meaningless while looking
entirely healthy. The probe made it worse than a theory: the default embedder
cannot identify itself. On 0.6.3 the object is an `ONNXMiniLM_L6_V2` instance
whose `.name` is `None` and which has no `get_config`; on 1.5.9 it is a wrapper
whose `.name()` is the string `"default"` and whose `get_config()` is `{}`. A
stamp written from either is not a stamp. So the substrate names the embedder
itself — `ONNXMiniLM_L6_V2`, i.e. `all-MiniLM-L6-v2`, sha256
`913d7300ceae3b2dbc2c50d1de4baacab4be7b9380491c27fab7418616a16ec3` — and passes
it explicitly on **every** open, so the library default can never decide the
model behind an existing collection.

**The deny-list corpus.** The `fabric` scope was a whole-tree deny-list
(`EXCLUDE_PARTS`) where the peer charter and `scripts/sparknet-rag-corpus.py`
mandate an allow-list. Measured before the change: 138 markdown files, 1,699
chunks, of which **1,090 chunks (64%) were personal or runtime pages** — handed
to every node in the fabric. After: **28 markdown files, 381 KiB, 242 chunks**,
none of it personal.

## The stamp, and which differences refuse

`embedding_model`, `embedding_sha256`, `corpus_digest` **refuse** (exit 3 →
503 on the wire). `chroma_version` is **reported only**: the library version is
not what makes a distance meaningful — the model and the corpus are — and
refusing on a version difference would train every operator to ignore the
refusal. The corpus digest is what makes "reindex on any change" checkable
rather than a habit; `make chroma-stamp` compares the index with this build.

## Decisions worth keeping

- **The pin follows the design's literal `>=0.5,<1` (0.6.3), not the current
  1.5.9.** The bound is a reviewed contract, and a smaller upgrade surface is
  the point of a bound. The model identity comes from the explicit embedder and
  the stamp, not from the bound.
- **One policy, two allow-lists** (`NODE_ROOTS` / `FABRIC_ROOTS`, a strict
  superset) rather than two copies of the rules — a second copy of an
  allow-list is a second answer to "what is safe to serve", and the two copies
  drift. `ROOT_FILES` became `NODE_ROOTS`; the default is still `node`, so
  peer-node's webui workspace is unchanged.
- **The numeric trigger** for re-opening Milvus/Qdrant is now written down
  (design F2): **>100,000 chunks**, **p95 > 200 ms** over 1,000 queries, or a
  **third host** joining the fabric. Until one holds, the embedded client *is*
  the store.

## Gotchas this session paid for

- **`chroma-hnswlib` is not `hnswlib`.** chromadb 0.6.3 depends on the fork
  `chroma-hnswlib==0.7.6`, which provides the `hnswlib` import name chromadb
  expects and carries `Index.file_handle_count`. The plain PyPI `hnswlib`
  (0.7.0, 0.8.0) must never be installed alongside it — it lacks the attribute
  and the import breaks at collection creation.
- **No aarch64 wheel for `chroma-hnswlib`**, so pip builds it from source on
  the node: minutes, a compiler, and an interrupted build that leaves a 0-byte
  `.so` behind. `/tmp` is also reaped between tool calls, so scratch state
  belongs in the gitignored `.state/`.
- **Chroma caches its storage system per path** (`SharedSystemClient` is keyed
  by the persist directory). Deleting the index directory and reopening it *in
  the same process* hands back the cached state — the very state that was just
  deleted. That is why the index now records the chromadb version in a plain
  marker file next to it, and why the discard happens **before** any client
  opens the directory.
- **An upsert is not a rebuild.** `upsert` writes the ids that are in the
  corpus; it does not remove the ids that *left* it. A passage that was
  shortened left its old chunks behind while the corpus digest still matched —
  the digest hashes what was *written*, not what is *stored*. The index is now
  made equal to the corpus, and the count is asserted to follow it.
- **A traceback is the absence of a failure mode.** The first round trip
  against a real chromadb answered a 1.5.9-written index with a Python
  traceback (`StopIteration` inside chroma's segment manager). It is now a
  clean exit 3 with the rebuild command.

## Master build plan Step 2 — the registry's shape, stated once and checked

The fabric plan is `current: done`, so the next work was the plan-designated
one: `master-node/plans/MASTER_BUILD_PLAN.md` **Step 2** — "Registry schema and
the spec/impl boundary". The step had been reopened on 2026-10-06 because its
DoD (1) was *false*, not merely unverified.

### What the draft schema got wrong

The draft `master-node/manifests/registry.schema.json` described a shape
nothing produces, in three independent ways: it required `role: "registry"`
(no document carries a `role` at the document level), `schema_version:
"1.0.0"` (the shipped registry says `1.0`, and the peer's own test *pins*
`"1.0"`), and an entry field named `signature` while the one implementation
emits and verifies **`signature_b64`**. Worse: **nothing loaded the file** —
no test, no script, no make target — so it validated nothing at all.

### The decision, taken from the implementation

The canonical shape was **decided from what runs**, not guessed from prose:
it is what `shared/sparknet-authz.py` signs and evaluates — document
`{schema_version "1.0", master_public_key_b64, description?, authorizations[]}`,
entry `{fingerprint, identity, capabilities, overlay_ipv4, issued_at,
expires_at, revoked?, signature_b64}`. It is now stated **once**, in
`contracts/registry-schema.json`; the Master's path is a **symlink** to it,
because the contracts README forbids a value duplicated into a role dir and two
copies of a shape would drift.

### The checker, and why it is standard library only

`shared/sparknet-registry-schema.py` checks a document against that contract:
fields present and absent, types, the fingerprint against the identity it
carries, the closed capability vocabulary, and each entry's signature under the
key the document names. It reads **the standard library only**, deliberately:
the fabric's runtime dependency allow-list is `cryptography` alone, CI installs
exactly that plus pytest and ruff, and `make bundle-verify` runs the role's
suite inside a bundle venv — a validator needing `jsonschema` would pass here
and fail on a node. A schema keyword the checker does not implement is
**refused**, not ignored: a rule nobody enforces is a rule that quietly stops
being true.

### DoD (2) asserted in the direction that is still true

DoD (2) asked the suite to assert that the subvault *declares itself unbuilt*.
That was true when the step was written and became false when the first
executable surface landed (Step 15) — asserting it now would assert a lie.
The honest inversion: the role **declares** its build state (`MISSION.md`
frontmatter, `status:`) and the declaration must agree with the tree *and*
with the plan's open steps, so it cannot rot into a false claim in either
direction. DoD (3): every page in `docs/` declares a `status:` from a closed
vocabulary (`built`, `partially-built`, `unbuilt`, `preserved-not-wired`), and
any page that is not `built` carries a callout marker.

### Two stale claims, in both directions

`docs/master-control-plane.md` said the role "has no `scripts/`, `services/`
or `systemd/` directory" — false since Steps 15–16. `docs/killswitch-template.md`

## Master Step 5 — the guard approval issuer, and the three shapes that never met

### What the step actually found

The plan said "half built, half missing": issue and nonce tracking existed,
delivery was intent-only, and no integration test existed. The first two were
true; the real defect was worse. Three implementations of "an approval" were
live at once:

| Side | Shape it signed/verified |
|---|---|
| `master-node/scripts/sparknet-approval-issue.sh` | `{target, content_digest, nonce, issued_at}` |
| `master-node/services/sparknet-signer.py` | `{peer_fingerprint, guard_protocol_version, target_path, action, expires_at}` |
| `peer-node/services/sparknet-guard-d.py` | `{file_path, content_b64, content_sha256, issued_at, expires_at, nonce, request_id}` |

Every side was internally consistent, every side's own tests passed, and **no
approval the Master could mint was one a peer would accept**. "Half built" was
generous: the two halves had never met. The integration test is what makes that
kind of disagreement impossible to keep: signing here and verifying there is
the only check that spans the seam.

### The rule, once

`shared/sparknet-authz.py` gained `GUARD_APPROVAL_FIELDS`,
`GUARD_APPROVAL_REQUIRED` and `guard_approval_message()`. Eight fields, compact
sorted JSON (`json.dumps(..., sort_keys=True, separators=(",", ":"))`), strict
in both directions — a missing field **and** an extra field are refused, because
the signature covers exactly the projection and anything outside it is unsigned.
The signer and the guard both call it; each had its own copy before, which is
precisely how they drifted.

The lists are sorted because they are projections, not sequences. The *reading*
order (what an approval means, field by field) is the contract's
`field_semantics` map, which keeps it.

### Two holes closed while the shape was being fixed

1. **Peer binding.** The envelope now names the peer (`peer_fingerprint`). Before,
   an approval minted for peer A was a valid approval peer B could apply, as
   long as it protected the same path — the signature said nothing about who it
   was for. The peer refuses `wrong_peer` (403).
2. **No capabilities in the payload.** The peer reads `guard-apply` from its own
   signed registry entry. A payload that carried capabilities could grant the
   authority it is checked against.

### Transport, concretely

`POST /api/v1/critical-file/patch` on port 9090, body
`{"payload": <b64 canonical bytes>, "signature": <b64 Ed25519>}`. Two script
bugs were found on the way: the old issuer double-base64-encoded the signature
(`authz.sign_bytes` already returns base64, so `base64.b64encode` on its result
was wrong), and the deliver script built `http://10.100.0.9/32:9090` from the
identity's CIDR-form `overlay_ipv4`. Both are fixed and both would have been
found only by pointing the code at a listening peer.

The signer's `sign-guard-approval` returns the signature **beside** the
envelope (`{"approval": {...}, "signature_b64": ...}`), never inside it: an
approval carrying its own signature is an approval the canonical rule refuses —
signed by the Master itself. The socket-path script had the same defect in
reverse and was fixed to match.

### Done-when, measured

- `make approval-issue` mints the envelope and spends the nonce
  (`$SPARKNET_STATE_DIR/approval_nonces.json`); a repeat is refused.
- `make approval-sign-socket` signs through the isolated signer and leaves a
  `signature_issued` ledger block (the production path).
- `make approval-deliver` resolves the peer from the signed registry by
  fingerprint and POSTs; `--url` overrides. It refuses a mismatched approval
  *before* sending.
- `master-node/tests/test_approval.py` runs the real peer guard daemon by path
  on loopback and gets `PATCH_VERIFIED_DRY_RUN`, plus `wrong_peer` and
  `capability_missing` negatives.
- `peer-node/tests/test_guard.py` gained the two refusals (wrong peer,
  field outside the envelope).
- `tests/test_contracts.py` asserts the contract, the shared rule and both
  implementations agree, and that neither role carries a second copy.

**Amended, not dropped:** the peer stub runs `--dry-run`, so the protected-file
*write* is not exercised — euid 0 plus `chattr` on a target node. What the test
proves is agreement across the seam; the write leg is a target-node checklist
item, said so in the plan and in `MISSION.md`.
