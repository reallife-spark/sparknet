## Step 61 — cluster job realization design

**Goal (user):** "map→reduce cluster jobs — let any node submit a large-scale
question that fans out across all nodes so the fleet answers as one
GPU-accelerated cluster", with two operator decisions taken up front: build a
**new design doc** rather than editing `CLUSTER_INFERENCE_DESIGN.md`, and treat
the Master's shared vector DB (port 4223) as **load-bearing, in scope, not
deferred**. Four further decisions taken in-session: embedded Chroma for v1 with
Qdrant as the named upgrade; increments ordered envelope → 4223 → ingress →
fan-out → reduce; the doc settles the envelope encoding *choice* while code
fixes go to increment 1; the 4223 build step lives in `MASTER_ADMIN_PLAN.md`.

### Recon: what already exists vs what doesn't

Built: `cluster-dispatch`/`cluster-serve` reserved (contract + authz frozenset),
`sign-cluster-job` (`sparknet-signer.py:528`), `cluster_job_message` +
`is_expired` (`sparknet-authz.py:493,544`), node AI stack as committed config.
In goSpark: router modes + `splitPrompt`, `internal/placement`,
`PlaceAndDispatch` (picks **one** node), the two capability constants, the
proto, NATS dispatch, `compute/compute_worker.py`. Missing: multi-subtask
construction, fan-out, reduce, `submit/status/result`, and anything binding
`4223`.

### The four defects (each cited in the doc)

- **D1 envelope.** Fabric signs ISO-8601 `created_at`/`expires_at` and always
  projects `conversation_id`/`running_summary`/`context`/`budget`
  (`sparknet-authz.py:464-490,565`); goSpark uses `int64` `*_unix` with
  `omitempty` (`cluster.proto:41-42`, `apiv1/types.go:183-189`) — a verifier that
  re-serialises without an omitted field produces different bytes. The signer's
  `_job()` fixture (`test_signer_isolation.py:226-233`) uses
  `context:{index}`, `budget:{max_tokens,deadline_s}`, `subtasks:[{node_id,role,
  prompt}]` — matching neither. `cluster_job_message` validates required fields,
  mode and a non-empty subtasks list, and **no shape**. `test_authz_golden.py`
  pins `authorization_message` and `admin_request_message` but **not**
  `cluster_job_message` — the one projection the whole arc rests on has no
  cross-language proof.
- **D2 egress.** `contracts/overlay.json` pins a peer's `AllowedIPs` to exactly
  `10.100.0.1/32`. Peer→peer is therefore impossible, so the parent design's
  "N separate signed one-to-one subtasks" emitted *by a peer* cannot happen at
  n ≥ 3. Resolution: at `peer_pair` it works either direction (the two members
  are Master↔peer and each already has the other's `AllowedIPs`); at
  `master_governed` the **Master** becomes the emitter (its egress is
  unrestricted, every peer already trusts it). Permanent egress widening is
  rejected — it hands every peer a permanent authority-plane edge to every other
  peer, which is what the broadcast rejection exists to prevent.
- **D3 corpus.** `sparknet-chroma.py:58` `EXCLUDE_PARTS` is a deny-list;
  `sparknet-rag-corpus.py` is an allow-list whose exclusions always win; the
  peer charter's RAG rule is allow-list. For a corpus served to every
  `cluster-serve` node, deny-by-remembering is the wrong failure mode.
- **D4 stale prose.** `CLUSTER_INFERENCE_DESIGN.md:77` still says
  `chromadb:8000` on the shared node network; the committed ai-stack compose
  points at `127.0.0.1:18000` and its header explains Ollama/Chroma come from
  the node's **out-of-repo `~/infra`** stack so the slice never declares a
  second store. Nothing in this repository binds `11434` or `18000`.

### The vector DB (Seam F), and how the industry patterns were weighed

Measured before deciding: the `fabric` corpus is **3.3 MB / 257 files / ≈2,300
chunks** at the script's 2000-char default, and grep found **no** Milvus,
Qdrant, pgvector, Kubernetes or k3s in any tracked Python/YAML/JSON/MD/TOML.
So: pattern 1 (native distributed, compute–storage separation) rejected for v1
but adopted as the *shape* and designated upgrade path — **Qdrant** over Milvus
because its standalone mode is one process and replicates without k8s. Pattern
2 (HA sharding + 2–3× replication + etcd/Raft) rejected: replication factor two
across two hosts tolerates no failure, and a second consensus plane next to
`sparknet-consensus.py` would create two membership truths. Pattern 3
(pgvector) rejected: needs postgres the tree doesn't have, strands the `chroma`
extra and the substrate script.

The chosen design is the **inverse** of all three: they assume the store is a
primary system of record needing distribution, whereas here it is *derived
state* — `plan_index`/`chunk_text` are pure and `upsert` is idempotent, so you
rebuild from source rather than replicate. You cannot corrupt it, only lag it.

Checklist mapping: memory quantified (2,300 × 384-dim HNSW ≈ <50 MB + ~90 MB
MiniLM ONNX, trivial beside vLLM on 16 GB); mesh already satisfied (4223 is
`overlay_only`, binds `10.100.0.1`), with `top_k ≤ 20` + 300-char snippets so the
1 Gbit link is never a surprise; **model consistency** is the item the code
currently fails — `pyproject.toml:29` pins `chromadb>=0.5` **unbounded above**,
so a library upgrade can swap the default embedding model under a live index and
every distance afterwards looks healthy while being meaningless. Fix in the
design: bounded pin, collection stamp (`embedding_model`/`chroma_version`/
`corpus_digest`), **503 on stamp mismatch**, full reindex on any model change.

Other Seam F decisions: one collection `sparknet-fabric`; embedded
`PersistentClient` behind our own listener on `shared/sparknet-http.py`, **not**
the `chromadb` server (no registry gate, API-key auth); server-side embedding
only (the wire cannot check which model produced a vector); `GET /v1/doc/{id}`
is how `context_refs` resolves — the parent note never said; `POST /admin/
reindex` is a loopback-only route; check order source → signature → registry →
**existing** `cluster-dispatch`/`cluster-serve` (no new capability) → shape →
stamp, fail-closed at every step; chunker **imported, never copied** (the
`sparknet-ledger.py:37` pattern) because a drifted chunker makes `context_refs`
resolve to the wrong text with nothing to notice. The invariant worth stating in
code: a job with `context.source: master_vector_db` that cannot get context is
**refused at dispatch** — a vector-store outage must never change what every
cluster job is grounded on while reporting success.

v1 ingestion is an explicit `make vector-reindex`, **not** a timer — Master
`units-check` (`master-node/Makefile:141`) loops only `*.service`, so a `.timer`
would force an unrelated target change into the same commit; the peer's
`sparknet-sync.timer` is the precedent when it lands.

### Follow-up: the skip itself was the defect (operator-directed)

Having found that Step 60's green was a skipping green, the fix is not "run it
once" — it is to remove the skip. `make shellcheck` now **provisions its own
pinned binary** and fails **closed** if it cannot:

- `SHELLCHECK_VERSION ?= 0.11.0` in the Makefile, pinned the way the Actions are
  SHA-pinned: the gate must not change what it enforces when a shellcheck
  release ships. A version bump is a reviewed commit.
- Not on `PATH` → download into `.cache/tools/shellcheck-<ver>/<arch>/` (arch
  detected from `uname -m`; x86_64/aarch64 only) and run that. Verified from an
  empty cache: *"not on PATH — provisioning v0.11.0 (aarch64)"* then
  *"shellcheck: 0.11.0 (…/shellcheck)"*, gate PASS.
- Cannot find **or** fetch ⇒ non-zero with the URL and the offline remedy
  (`install shellcheck on PATH`). Verified with a bogus proxy: `Error 1` from
  make, an explicit refusal message, no silent pass.
- New `make shellcheck-install` provisions without running the gate.
- Second run hits the cache; no re-download.

**Workflow deliberately unchanged.** The first attempt added a CI step calling
`make shellcheck-install`, which failed
`tests/test_ci.py::test_the_gate_workflows_call_the_local_gate`: the check is a
substring test (`f"make {name}" not in run`) and `make shellcheck` is a prefix
of `make shellcheck-install`, so CI still "re-implements" `shellcheck` in the
test's eyes. That invariant is correct and worth more than the convenience, so
the target became a developer-only aid and `gate.yml` was reverted to calling
only `make ci`. Because the target self-provisions, CI gets the pinned binary
with no workflow change — which is the better outcome anyway (one place owns
the provisioning rule).
